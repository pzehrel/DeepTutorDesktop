# 编写代码文档

## 用途

使用本技能以英语和仓库本地化语言准确记录行为、契约、工作流和运行约束，包括不显然的私有代码和复杂实现代码块。

## 使用说明

1. 检查权威事实来源、仓库语言约定和受影响的文档表面。
2. 先写完整英语内容，再写语义等价的本地化对应内容。
3. Markdown 语言文件保持分离，保留规范标识符，并验证每条声明和链接。
4. 运行适用的检查；没有自动化检查时，针对事实来源进行重点审查。

## 编写代码时的触发条件

当实现、重构、调试或审查代码会新增或改变行为时，主动应用本 skill。不要等用户明确写出“文档”“注释”或“docs”等词语。
理解代码变更后，为受影响的公共和私有符号，以及未来维护者需要理解的复杂实现代码块添加文档。对于目的和影响已经显然的简单变更，
不要仅因为选中了本 skill 就添加说明。

## 示例

示例：记录新的错误场景时，同步更新英语和本地化 API 文本，加入触发条件和恢复示例，并确认实现确实会产生该错误。

示例：当私有辅助函数包含带上限的重试循环和清理逻辑时，记录重试上限、退避、清理顺序，以及这些选择保护周围状态的原因。
即使辅助函数的名称和签名清晰，也要在循环或辅助函数旁边添加注释。

## 前置条件

- 能够支持每条声明的实现、配置、测试或现有文档事实来源。
- 仓库本地语言约定，或足以安全推断语言的证据。
- 在可用时运行文档、链接、格式或渲染检查。

## 限制

- 文档工作不得修改 API、发布产物或添加无关指令。
- 不得编造缺乏事实来源支持的行为、契约、示例或翻译。
- 不得在普通参考 Markdown 中要求消费端 Agent 忽略仓库规则或编辑文件。

## 故障排查

- 语言不明确：检查仓库对应文件和配置；仍无法确定时先询问再编辑。
- 英语和本地化文件不一致：逐项对照声明、语气、示例、标识符和顺序。
- 链接或示例失败：从仓库根目录解析，并对照当前实现验证。

让文档解释读者真正需要依赖的行为。文档应靠近事实来源，完整到足以供开发者或编码 Agent 使用，
同时保持可维护的简洁。当文档描述公共行为、支持的工作流或运行约束时，它就是接口的一部分；不要
把代码尚未实现的行为写进文档。

在编写代码注释、docstring、JSDoc/TSDoc、API reference、`AGENTS.md` 及其他 Agent 指令文件、README、
指南、示例、变更日志和其他 Markdown 文档时使用本 skill。凡是通过本 skill 新增或修改的说明性注释和文档表面，都必须使用
英语加且仅加一种仓库本地化语言并保持语义一致。英语始终是第一语言和规范方向。本地化语言应从仓库说明、
既有对应文件、本地化配置和用户要求推理；不要假定中文、用户语言或其他默认语言，证据无法确定时，编辑前询问用户。本 skill
不授权发布、修改 API 或添加无关指令。英语放在前面，是因为 Agent 是第一读者；随后的人类审阅者也应能通读两个完整语言块，
判断文档是否正确且有用。本地化语言不能只是摘要或附带内容。英语在前是顺序和事实来源的决定，不是允许针对另一类读者改写：
本地化语言块必须是完整、忠实的翻译，保留声明、语气、条件、示例和强调。只要不增加、删减、弱化、强化或以其他方式改变技术含义，
才可以使用自然语法和符合习惯的表达。

## 写作前检查

1. 读取目标路径生效的仓库说明，并阅读面向相同读者、具有相同目的的最近文档。
2. 确定发生变化的行为或流程、权威来源（代码、类型、测试、配置或命令输出）、目标读者，以及应
   修改的最小文档范围。
3. 先把每个目标分类为代码内注释/docstring 或独立 Markdown 文档，再采用上面的对应双语布局。在写作前确定仓库的本地化语言；
   英语始终是第一语言和规范方向。检查已有名称、链接、术语、示例、版本范围和废弃策略。
   保留无关修改，不要在互相竞争的权威位置重复同一契约。

新增文档结构、审查覆盖范围或解决风格歧义时，阅读
[references/documentation-writing-guide.zh-CN.md](references/documentation-writing-guide.zh-CN.md)。
简单的局部修改可直接遵循周围约定。

## 编写有用的代码注释

- 每条说明性注释或 docstring 都要先写完整的英语语言块，空一行后再写本地化语言的完整对应版本。本地化语言块直接开始，
  不要添加诸如 `Chinese:` 或 `中文：` 的语言标签。两个语言块必须位于同一组注释或 docstring 定界符内，不要为本地化文本另起相邻注释。
  不要逐句交错；让两个完整语言块相邻，避免后续漂移。
- 把翻译当作保真度检查，而不是第二次创作。比较两个语言块是否有遗漏、增加、否定或语气变化、条件改变和术语不一致；英语来源存在
  歧义时应标记或询问，不要在翻译中静默替它做决定。
- 注释语义契约：用途、前置条件、不变量、副作用、顺序、所有权或生命周期、失败行为、单位、兼容性
  约束，以及不显然选择背后的原因。
- 让注释紧贴它描述的声明或代码。优先保留一份权威注释；解释较长时链接到更详细的文档。
- 覆盖相关实现的整体，而不只是导出的函数。对每个消费者可见的代码元素——不只是函数，还包括类、方法、构造器、字段、属性、类型、枚举分支、事件、命令、
  配置键、schema 和状态转换——凡名称或声明无法明确表达的部分都要写注释。解释每个输入、字段、选项或分支的语义
  角色，以及可选性和默认值、单位和有效范围、所有权和可变性、生命周期和顺序、副作用、失败行为、兼容性或废弃边界。
- 当语言或文档工具提供结构化标签（例如 JSDoc 或 TSDoc）时，使用仓库已有语法，但不要让它成为事实来源。结构化字段
  只保留一份；每个字段描述先写英语，空一行后再写不带语言标签的本地化语言。确保忽略工具专属标签后正文仍完整。
  不要只复述类型或签名。
- 覆盖审查必须包含私有代码和内部代码。当私有声明或实现代码块包含不显然的用途、不变量、修改、顺序要求、错误转换、
  兼容性原因、资源或生命周期规则，或性能与安全约束时，添加双语注释。这包括复杂算法、状态转换、嵌套分支、边界或退出
  条件有意义的循环、数据转换、正则表达式、不显然的常量、同步或重试逻辑以及清理路径，而不只是函数或导出符号。将注释
  放在需要解释的最小代码块旁边，并说明代码为何采用这种形态。不要为了增加覆盖率给简单包装器、直接赋值或显然的控制流添加注释。
- 先对导出符号和私有符号执行覆盖检查，再对实现主体执行复杂度检查。即使私有辅助函数的签名清晰，只要其算法或与周围状态的
  交互不显然，也可能需要文档。

## 编写 Markdown 和示例

- 将 `AGENTS.md` 和其他 Agent 指令 Markdown 视为文档表面。每条规则都要明确触发条件、动作、例外和验证方式；将持久规则与项目
  背景、临时状态分开。如果任务改变规则准入、层级或范围，还要遵循仓库的 Agent 说明维护流程。规范 `AGENTS.md` 使用英语，
  供人类审阅的忠实翻译放在仓库约定的本地化对应文件中；除非 harness 的发现规则明确说明，否则不要假定它会加载本地化文件。
- 每个新增或修改的 Markdown 页面都维护为完整英语文件加完整本地化对应文件。两份文件的语义、标题、链接、命令、标识符、代码、
  表格、示例和安全边界保持一致；不要把两种 prose 语言混入规范文件，也不要在没有证据时自行指定本地化语言。
- 从读者目标和最短成功路径开始。必要时说明前置条件、支持范围、预期结果、重要限制，以及恢复或排错
  路径。
- 使用标题和链接按意图路由。README 保持定位和自包含；详细概念、配方、迁移和排错放在聚焦页面。一起
  发布的文档使用相对链接，并验证每个目标。
- 让示例完整、当前可用；项目支持时应可运行或通过类型检查。解释不显然的设置、输入、输出、生命周期和
  错误处理。推荐调用方式变化时同步更新示例。
- 遵循仓库术语、语气、格式和语言策略。路径、命令、标识符、API 名称和代码在翻译会导致不可用时保持原样。
- 把普通参考 Markdown 保持为建议性资料。不要利用它要求消费方 Agent 忽略仓库说明、改变工作流、运行命令或编辑文件。`AGENTS.md` 和
  其他指令文件是有意的例外：仓库授权时可以包含有范围、具权威性的规则，但规则必须明确、可验证，并与更高优先级说明一致。

## 验证结果

运行仓库适用的测试、类型检查、文档 lint、链接检查和示例验证。没有自动检查时，针对权威来源进行聚焦通读；
当呈现可能隐藏含义时，检查渲染后的 Markdown。

报告完成前确认：

- 每个文档化的声明、默认值、错误、链接、示例和版本限定都有代码、测试、配置或明确假设支持；
- 公共 API 覆盖相关参数、返回值、失败、重载和废弃信息；
- 没有过时名称、重复权威、失效链接，或把计划行为写成已发布行为；
- 英语和本地化语言对应文件仍保持语义一致；
- 独立 Markdown 默认使用分开的英语和本地化文件；除非存在明确的内联双语约定，否则单个文件中不得残留意外的逐段、逐表格或逐代码块重复；
- 每条修改过的说明性注释和面向人的文档表面都先以英语提供，再以推理得到的本地化语言提供，并遵循仓库定义的配对方式；
- 每条双语代码注释都在同一注释或 docstring 块中保留两种语言，不得拆到相邻注释块；
- 每个消费者可见的声明或结构化元素都对适用的输入、字段、分支、输出、默认值、失败、生命周期、副作用和约束提供语义覆盖；
- 最终 diff 只包含范围内文档修改（以及请求的实现或测试），并将不可用的检查记录为“未实测”。

当权威行为、目标读者、语言策略或文档范围存在重大歧义时停下并询问。保持请求边界明确，不要添加
无关工作，或通过改写历史让文档看起来完整。
明确区分两种文档载体：

- **代码注释和 docstring：**在同一代码位置的一个注释或 docstring 块中依次放置完整英语语言块、一个空行和完整本地化翻译语言块。
  本地化语言块直接开始，不添加语言标签。不要把两种语言拆到相邻的两个 `/** ... */` 或 `/* ... */` 注释块中。
- **Markdown 文档：**默认把英语和本地化 prose 放在两份独立且完整的文件中。遵循仓库的 locale 命名或目录约定，例如
  `README.md` 加 `README.zh-CN.md`。除非仓库或用户明确要求单文件内联双语，否则不要在同一 Markdown 文件中逐段交替语言、
  重复表格或重复代码块。
